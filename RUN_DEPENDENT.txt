# Quantities that differ between two runs of the SAME program

## Scope: only verification that COMPARES two texts

This catalog applies to exactly one kind of check — one that compares a fresh
run's OUTPUT against a stored GOLDEN, line by line. In this tool's plan schema
those are the assertion kinds:

* `text_lockstep` — the whole output compared line for line;
* `field_assertion` — the same, comparing declared columns of a table.

It does NOT apply to the other kinds, and forcing it onto them is a mistake:

* `self_report` — the verdict comes from numbers the PROJECT prints about
  itself (a pass/fail count, an error count). There is no golden text to
  compare and no per-run line to suppress; the reader names the numbers it
  read and compares them to declared floors. A "timestamp" in that output is
  simply never read.
* `artifact` — the check is that a file EXISTS and is non-empty. No text.
* `metric` — one number is extracted by a declared pattern and compared to a
  declared value.

So: **if a verification has no golden comparison, this file has nothing to say
about it**, and adding a `drop`/`keep`/`mask` there would be a rule the
mechanism never reads (the plan schema refuses such a key by name).

A comparison of two runs of one binary sees differences that are NOT
differences in what it computed. They come from the RUN — the clock, the
memory layout, the environment — never from the input. Every one of them is a
source of a **false FAILURE**, and, if suppressed carelessly, of a **false
PASS**.

This file is the CATALOG. Read it when a diff appears, to recognize which
category the differing line belongs to. **It is a generator of HYPOTHESES,
never a suppressor** — read "The one danger" at the end before using it.
**And it speaks only to a golden comparison** (see Scope above): for a
`self_report`, an `artifact` or a `metric`, there is no line to suppress and
this file does not apply.

Get the evidence first, do not eyeball the output:

    python3 bench.py evidence <build dir> --shift-date
    # two reference runs (the second under a shifted TZ), reporting the line
    # shapes that moved and are NOT yet covered by the plan's own rules

## The categories

| # | category | what the line looks like | usual mode |
|---|---|---|---|
| 1 | **Clocks** | a date, a wall/CPU/elapsed time, `N SECONDS`, a "time estimate", a progress percent, uptime, a per-step timer | `drop` if the line is ONLY a clock; `mask` if it shares the line |
| 2 | **Memory addresses** | a pointer, an "address of", a pool/heap/stack base, an allocation offset, `%p`, bare hex | `mask` the address; `drop` only if the WHOLE line is addresses |
| 3 | **Absolute paths** | a build dir, source root, tmp dir, home, install prefix, `argv[0]`, an absolute path in a diagnostic | `mask` the varying prefix |
| 4 | **Process identity** | PID, PPID, TID, session id, job id | `mask` |
| 5 | **Machine / user identity** | hostname, FQDN, username, uid, domain, node name | `mask` |
| 6 | **Randomness / session id** | UUID/GUID, a seed, a nonce, a `mkstemp` name, hash-map iteration order | `mask` |
| 7 | **Environment-derived** | CPU count, memory size, load average, free disk, terminal width, locale, `TZ` | `mask` or `drop` |
| 8 | **Filesystem metadata** | a file size, mtime, inode, device number, "bytes written" | `mask` |
| 9 | **Concurrency order** | lines or float SUMS whose order depends on scheduling | **not a line rule** — see below |
| 10 | **Uninitialized / padding** | bytes never assigned, stack garbage in a hex dump | `mask` |
| 11 | **Build / version stamps** | a compiler version string, a build date, a VCS revision, "built by" | `mask` or `drop` |

**Deliberately NOT in this list: near-zero floating-point noise** (a residual
around 1e-18 whose SIGN is meaningless). That is not a run-dependency — it is a
numerical-tolerance matter, and the plan's `rtol`/`atol` is where it belongs.
Treating it as a line to drop would stop comparing the magnitude too.

## The saturation trap — category 2's dangerous form

A fixed-width field that cannot hold its value SATURATES: an integer field of
width 8 printing a 9-digit number emits a run of `*` instead. **Two DIFFERENT
values then print as the SAME string and compare EQUAL**, so the error
direction is always a **false PASS**.

The consequences are specific:

* a line that saturates in BOTH runs looks like a perfectly stable constant,
  so nobody thinks to declare it — until one run happens to fit the field and
  the comparison suddenly fails;
* therefore **"this line looks stable" does NOT mean "this line did not
  move"**. For a fixed-width field, stability is the symptom, not the
  evidence.

To confirm a suspected saturation: **widen the field temporarily and rebuild**,
then run several times. If the values are then all different, the field was
hiding differences rather than showing them.

This is where `mask` is not optional. Such a field almost always shares its
line with stable, meaningful values, so `drop` would stop comparing those too.
Mask the FIELD, keep the line.

---

## Category 9 is not a line rule

An order that depends on thread scheduling, on an unordered container, or on a
parallel reduction is not fixed by `drop`/`keep`/`mask` — those act on lines,
and the problem is the line ORDER. A float sum is worse: reordering changes the
result through non-associativity, which is a genuine numeric difference, not a
formatting one. Such an output needs either a comparison that is order-blind
(sort before comparing) or a different assertion kind. Say so; do not force it
into a line pattern.

---

## The one danger

**Classifying a diff as "reasonable" is exactly how a real difference gets
hidden.** The catalog exists to help you write a rule, never to let a diff be
ignored: an automatic "this looks like a timestamp, skip it" is the same
failure as any other check that did nothing while reporting success.

So:

1. **The catalog gives a HYPOTHESIS; a measurement CONFIRMS it.** Two runs of
   the same binary (`bench.py evidence`) show what actually moved. A line that
   LOOKS like a clock but is a judged value is the worst possible thing to
   suppress.
2. **Write the MINIMAL rule, and prefer `mask` to `drop`.** `drop` silences
   everything on the line; if any of it is judged, the gate just got quieter.
3. **The rule lives in the PROJECT'S OWN DECLARATION** (the verification
   protocol), not in the tool — explicit, readable, and reviewable by whoever
   comes next.
4. **Re-measure after writing it.** `bench.py evidence` must come back with
   nothing left uncovered, and the verdict must hold on a FRESH capture — a
   single PASS proves nothing, because the difference is intermittent by
   nature.
